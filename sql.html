Making two slow SQL queries faster

Two SQL rewrites that reduce intermediate work while preserving the original query semantics and edge cases.

SQLCourse projectDuckDBWindow functionsQuery plans
Dataset

120,000 pageviews
3,000 users

Environment

DuckDB 1.4.5
One thread, in-memory tables

Measurement

One warm-up, then three timed executions with full result retrieval.

The problem

Two starter queries answer useful behavioral questions: how many sessions occurred, and which users first landed on the pricing page? Their plans build and reduce large sets of candidate row pairs, doing more work than the questions require.

Rewrite one: sessionization

LAG(ts) over each user’s ordered events replaces the correlated predecessor lookup and its joins. The optimized plan uses one pageviews scan and a window operator.

137.68 → 17.80milliseconds, local median
7.73×local measured speedup

The original inner hash join emits 4,919,154 rows; the optimized window emits 120,000. Both queries return 118,889 total sessions.

Rewrite two: first-touch attribution

ARG_MIN(url_path, STRUCT_PACK(ts := ts, view_id := view_id)) identifies each user’s first path in one grouped pass. The query considers all history before applying the pricing-path filter.

18.05 → 4.23milliseconds, local median
4.27×local measured speedup

The optimized aggregate emits 3,000 user rows, compared with 689,908 rows from the starter’s inner hash join. Both return 412 first-touch-pricing users.

Correctness is part of performance work

Tests compare the answers against independent Python implementations and cover timestamp ties, exactly 30-minute gaps, minute-boundary behavior, earlier visits, missing dates, and empty input.

The session query preserves date_diff('minute', ...) > 30. Replacing it with a superficially similar elapsed-time comparison would change some boundary cases. Both rewrites keep the original timestamp tie-breaker.

I checked the edge cases before calling the rewrite finished.

What the benchmark supports

These are saved local measurements, not a production latency promise. Each timing is the median of three runs after warm-up. The stronger structural evidence is fewer scans, removed joins, and reduced intermediate row counts.

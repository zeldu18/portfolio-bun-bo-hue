Building a customer-orders pipeline

A customer-orders data pipeline that turns raw orders and payments into a tested, reconciled customer mart.

The problem

An order can have multiple payments. Joining raw payments directly to orders can silently multiply order counts. A useful customer mart needs the right grain, exact monetary totals, and checks that catch problems before they become someone else’s dashboard.

What I built

A dbt project with staging models and a customer-orders mart in DuckDB, orchestrated with Dagster and packaged with Docker. Payments are grouped by order before aggregation. Only completed or shipped orders contribute, and qualifying orders with no payment contribute zero to the amount.

Proving that the outputs are right

The checks cover uniqueness, non-null fields, relationships, order counts, amounts, date ordering, and reconciliation to source orders. An independent Python calculation verifies the exported rows.

The staged incremental demonstration starts with 2,500 orders through March 2025, then loads the remaining orders. Both the incremental staging table and final mart match a full refresh row for row. Running again without new data leaves the results unchanged.

Making failure visible and recoverable

The daily schedule runs at 02:00 UTC. In the recorded verification, a deliberately flaky task fails once, retries, succeeds, and allows the build, tests, freshness inspection, and export to finish.

The historical fixture triggers a freshness error because its latest order is from June 2025. The orchestration explicitly inspects that known fixture condition; it does not silently treat all freshness failures as acceptable.

What I learned

Incremental processing was correct. On this small fixture, it wasn’t faster.

The saved all-model run took 1.629 seconds incrementally versus 1.553 seconds for a full refresh, including startup and parsing overhead. Processing fewer rows did not translate into a demonstrated speedup at this scale.

The append-only rule also assumes new orders arrive after the maximum stored order date. For late-arriving or updated orders, I would add a lookback window and a unique-key merge rather than rely on that boundary.
